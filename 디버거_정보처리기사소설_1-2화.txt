 📒 도윤의 오답노트 #1
──────────────────────────────────────────────

 ■ 이상 현상 (Anomaly) ─ "삽·삭·갱"
   · 삽입 이상 : 데이터를 넣을 때 원치 않는 값까지 함께 넣어야 하는 문제
                 (예: 주문이 없으면 상품을 등록할 수 없음)
   · 삭제 이상 : 데이터를 지울 때 필요한 정보까지 함께 지워지는 문제
                 (예: 유일한 주문을 지웠더니 상품 정보까지 사라짐)
   · 갱신 이상 : 중복된 데이터 중 일부만 수정되어 불일치가 생기는 문제
                 (예: 상품명이 행마다 다름)
   → 원인은 '중복'. 해결책은 '정규화'.

 ■ 함수 종속
   · X → Y : X 값을 알면 Y 값이 하나로 정해진다. (X = 결정자, Y = 종속자)
   · 완전 함수 종속 : 기본키 '전체'에 종속
   · 부분 함수 종속 : 복합 기본키의 '일부'에만 종속  ← 2NF에서 제거
   · 이행 함수 종속 : A→B, B→C 이면 A→C           ← 3NF에서 제거

 ■ 정규화 순서 ─ "도·부·이·결·다·조"
   1NF  : 도메인이 원자값만 갖도록
   2NF  : 부분 함수 종속 제거
   3NF  : 이행 함수 종속 제거
   BCNF : 결정자이면서 후보키가 아닌 것 제거
   4NF  : 다치(다중값) 종속 제거
   5NF  : 조인 종속 제거

 ■ 반정규화 (참고)
   · 성능을 위해 일부러 중복을 허용하는 것. 정규화의 반대 방향.
   · "역정규화"라고도 한다.

   class DiscountSettle implements SettleStrategy { public void settle() { /* 할인 */ } }
   class RefundSettle  implements SettleStrategy { public void settle() { /* 환불 */ } }
   class CouponSettle  implements SettleStrategy { public void settle() { /* 쿠폰 NEW */ } }

 📒 도윤의 오답노트 #2
──────────────────────────────────────────────

 ■ 결합도 (Coupling) ─ 모듈 '사이'의 의존 정도. 낮을수록 좋다.
   약 ──────────────────────────────→ 강
   자료 < 스탬프 < 제어 < 외부 < 공통 < 내용
   "자스제외공내" (자스민 제외하고 공짜로 내줘)

   · 자료   : 필요한 데이터 값만 주고받음
   · 스탬프 : 배열, 레코드, 객체 같은 자료 구조를 통째로 넘김
   · 제어   : 상대 모듈의 처리 흐름을 바꾸는 제어 신호(플래그)를 넘김
   · 외부   : 외부에 선언된 데이터를 여러 모듈이 참조
   · 공통   : 공통(전역) 데이터 영역을 여러 모듈이 함께 사용
   · 내용   : 다른 모듈의 내부 기능이나 데이터를 직접 참조·수정

 ■ 응집도 (Cohesion) ─ 모듈 '안'의 요소들이 얼마나 뭉쳐 있나. 높을수록 좋다.
   강 ──────────────────────────────→ 약
   기능 > 순차 > 교환 > 절차 > 시간 > 논리 > 우연
   "기순! 교절! 시논우!"

   · 기능적 : 모든 요소가 하나의 기능만 수행
   · 순차적 : 한 활동의 출력이 다음 활동의 입력으로 쓰임
   · 교환적 : 같은 입력·출력 데이터를 사용하는 요소들이 모임 (= 통신적 응집도)
   · 절차적 : 여러 기능을 정해진 순서대로 수행
   · 시간적 : 같은 시점에 처리되어야 하는 것들을 모음 (예: 초기화 루틴)
   · 논리적 : 유사한 성격의 처리를 모아두고 그중 하나를 골라 실행
   · 우연적 : 서로 관련 없는 요소들이 모임

   ★ 짝꿍 공식: 플래그로 분기 → 밖에서는 '제어 결합도', 안에서는 '논리적 응집도'
   ★ 좋은 설계 = "결합도는 낮게, 응집도는 높게"

 ■ GoF 디자인 패턴 (총 23개 = 생성 5 + 구조 7 + 행위 11)
   · 생성 (5) "추빌팩프싱"
       추상 팩토리, 빌더, 팩토리 메서드, 프로토타입, 싱글톤
   · 구조 (7) "어브컴데퍼플프"
       어댑터, 브리지, 컴포지트, 데코레이터, 퍼사드, 플라이웨이트, 프록시
   · 행위 (11) 나머지 전부
       책임 연쇄, 커맨드, 인터프리터, 이터레이터, 미디에이터, 메멘토,
       옵저버, 상태, 전략, 템플릿 메서드, 비지터

 ■ 오늘 나온 패턴
   · 싱글톤 (생성) : 클래스의 인스턴스를 오직 하나만 생성, 어디서든 그것을 공유
                     → private 생성자 + static getInstance()가 보이면 싱글톤!
   · 전략   (행위) : 알고리즘을 각각 캡슐화하여 상황에 따라 교체해 사용

 ■ 코드 출력 문제 팁
   · getInstance()로 얻은 변수들은 이름이 달라도 '같은 객체'다.
   · ++count 는 '먼저 증가 후 반환', count++ 는 '반환 후 증가'.
     (오늘 코드는 ++count라서 1, 2, 3, 4)
